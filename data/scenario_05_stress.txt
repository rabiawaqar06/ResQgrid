# ==========================================================================
# Scenario 05 - Stress scenario (120 locations)
# --------------------------------------------------------------------------
# PURPOSE
#   Meets the Section 5 stress requirements and is at least twice the
#   provided scenario in every dimension (56/117/12/60/250 in the
#   provided file):
#     locations 120, connections 260 (12 initially BLOCKED),
#     robots 24, requests 150, events 60, max_steps 600.
#   Used in Submission 2 for timing and scalability measurements.
#
# LAYOUT
#   A grid of locations with random diagonal shortcuts. Costs 2-12.
#   Generated by a seeded script (seed 2026), so it can be regenerated
#   exactly and scaled to larger sizes for the performance analysis.
#
# WHAT IT TESTS
#   1. Scale: per-step work must stay fast when V, E, R and Q double.
#   2. Location 67 is cut off at the start (all its connections BLOCKED);
#      Requests 3 and 12 are there. Restored at t=180.
#   3. Bursts: 10 requests at t=0 and 8 requests at t=100 (all urgency 3
#      at t=100), so tie-breaking is exercised at scale.
#   4. A mix of all event types: road blocks with later restoration,
#      charging stations down/up, robots offline/online, urgency raises.
#   5. Robots 1, 6, 11, 16 and 21 start at half battery, so charging is
#      needed early.
#
# EXPECTED BEHAVIOUR (checked as invariants, not as an exact trace)
#   - No request is ever assigned to two robots at once.
#   - No robot ever has battery < 0 or > max_battery.
#   - No robot ever traverses a connection while it is BLOCKED.
#   - Two runs produce byte-identical output logs.
# ==========================================================================
